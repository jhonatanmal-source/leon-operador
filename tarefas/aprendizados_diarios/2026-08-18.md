- ## Gap de dados 12-17/08 ERA recuperável — erro de diagnóstico no caminho do tar (MISSION-20260818-BACKUP-RESGATE-DADOS)

**O que estava registrado:** o handoff (pendência #6) e o aprendizado de 17/08 afirmavam que o gap era "NÃO recuperável integralmente" porque "backups vão só até 05/08".

**Realidade:** existem backups full diários em `/opt/leon/backups/` (15, 16, 17, 18/08). O de **17/08 às 03:18 é anterior ao incidente das 21:03** e preservou a janela perdida: 225 linhas em `data/pre_operation_trades.csv` contra 74 do arquivo truncado.

**Causa raiz do erro de diagnóstico:** os caminhos internos do tar são `data/...`, **não** `app/data/...`. A verificação anterior extraiu pelo caminho errado, recebeu saída vazia e concluiu ausência de dados. Um `tar -xzf ... -O app/data/arquivo.csv` inexistente retorna vazio **com exit 0**, sem erro visível.

**Verificador (padrão a adotar):** antes de declarar dado irrecuperável, listar a estrutura real do arquivo (`tar -tvzf | grep arquivo`) e conferir o prefixo dos caminhos. Nunca concluir ausência a partir de extração vazia — validar que o membro existe no índice do tar. Extração silenciosa vazia é falso negativo.

**Resgate executado:** merge não-destrutivo (dedup por ID, precedência do registro atual) elevou 73 → **297 pre-ops** (PREOP-003106→003550), recuperando **224 IDs**, dos quais **103 fechados com resultado**. Integridade: 30 campos em todas as linhas, 0 duplicatas.

**Padrão de aplicação segura em CSV de produção:** (1) snapshot antes de escrever; (2) parar o processo escritor para evitar concorrência; (3) **regenerar o merge a partir do arquivo atual**, não de um staging antigo (o meu tinha ~3h); (4) `cp` para temp no MESMO filesystem + `mv` (rename atômico), preservando `perm`/`owner` capturados com `stat`; (5) validar com parser CSV real; (6) reiniciar o escritor e revalidar.

**Armadilha do awk em CSV quotado:** `awk -F';'` reportou 17 linhas com 32 campos, sugerindo corrupção. Falso positivo — o campo `observacao` é quotado e contém `;` interno (`"...STOP LOSS; preco 4356.4; lucro -7.73."`). O parser `csv` do Python confirmou 30 campos em 100% das linhas. Verificador: validar integridade de CSV sempre com parser que respeita aspas, nunca com split por delimitador.

## Bug MCP: `_MT5_AVAILABLE` copiado por valor no import (pendência #12)

**Sintoma:** `get_account_info`, `get_current_price`, `get_ohlc`, `get_market_snapshot`, `list_symbols` retornam sempre "MT5 não disponível", mesmo com MT5/rpyc saudáveis (porta 18812 aberta, wineserver ativo). Só `check_mt5_status` funciona.

**Causa raiz:** `src/mcp/leon_market_mcp.py` faz `from mt5_safe import _MT5_AVAILABLE` — isso copia o valor `False` no import. A flag só vira `True` dentro de `mt5_safe._ensure_initialized()`/`check_mt5()`, mas os handlers checam a cópia estática e nunca chamam a inicialização antes. Verificado: `check_mt5()['available'] == True` mas `_MT5_AVAILABLE` (no módulo MCP) continua `False` depois.

**Verificador (padrão a adotar):** flags de disponibilidade mutáveis nunca devem ser importadas **por valor** — importar o módulo (`import mt5_safe`) e ler `mt5_safe._MT5_AVAILABLE` dinamicamente, ou expor uma função (`check_mt5()`) que os handlers chamem antes de qualquer uso. Importar `False`/`True` por valor cria falso negativo permanente sem erro visível.

**Status:** SEM correção (fora do escopo da missão). Registrado no handoff como pendência #12.

## Pendência #2 — Telegram alinhado como DESABILITADO (config + doc)

**Sintoma:** handoff dizia "Telegram desabilitado", mas o runtime reportava `TELEGRAM_ENABLED = True` (via `config.ini` `enabled = true`), sem token (vazio) — ou seja, estado inconsistente: `enviar_mensagem()` retornava `TELEGRAM_CONFIG_MISSING` em vez de `TELEGRAM_DISABLED`.

**Causa raiz (3 fontes divergentes):**
- `config.ini` `[TELEGRAM]` → `enabled = true`, token/chat_id vazios (fonte efetiva do runtime — `telegram_config.py` lê `ROOT_DIR/.env` + `config.ini`).
- `/opt/leon/app/.env` → arquivo real (não symlink) SEM chaves Telegram.
- `/opt/leon/config/.env` → `LEON_TELEGRAM_ENABLED=false` + token placeholder `COLAR_...`, **NÃO lido pelo runtime**.

**Detalhe crítico:** o `CONTEXTO_EVOLUCAO.md` (22/07) dizia que o Telegram lia de `/opt/leon/config/.env` via symlink `app/.env -> config/.env`. **O symlink não existe mais** (foi sobrescrito em 27/07 por um `.env` real com chaves web). Se o symlink fosse recriado com o token placeholder `COLAR_...` presente, o placeholder seria lido como token "configurado" → risco de POST com token inválido. **Não recriar o symlink enquanto o token for placeholder.**

**Correção aplicada:** `config.ini` `[TELEGRAM] enabled = true` → `false` (o `config.ini.example` já tinha `false` — o exemplo estava correto). Validado: `TELEGRAM_ENABLED = False`, `enviar_mensagem()` retorna `{'ok': False, 'error': 'TELEGRAM_DISABLED'}`; 39 testes telegram + suíte completa **398 passed**.

**Reativação futura (fluxo):** token real do BotFather em `/opt/leon/config/.env` → garantir leitura pelo runtime (env var ou `app/.env`/symlink com token real) → `config.ini` `enabled = true` → teste de envio real.

**Verificador (padrão a adotar):** o estado real de uma integração deve ser verificado pelo **runtime** (`import src.telegram_config; TELEGRAM_ENABLED`), nunca pela documentação ou pelo `.env` fora do caminho lido — o que está escrito num arquivo que o código não lê é apenas intenção.
