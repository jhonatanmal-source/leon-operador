- ## Correção: `_process_running` — substituição de PowerShell por verificação nativa Linux

**Arquivo:** `web_app/services/system_health_service.py`

**Problema:** A função `_process_running()` usava `subprocess.run(["powershell", ...])` com cmdlets Windows (`Get-CimInstance Win32_Process`), o que falha no Linux (Ubuntu 24.04).

**Solução:** Substituída por:
1. **Primário:** `psutil.process_iter(["cmdline"])` — itera processos e verifica se o fragmento está no cmdline
2. **Fallback:** `subprocess.run(["pgrep", "-f", fragment])` — caso `psutil` não esteja disponível

**Assinatura mantida:** `def _process_running(fragment: str) -> bool`

**Comportamento preservado:**
- Mesmo parâmetro (`fragment`), mesmo retorno (`bool`)
- Tratamento de exceções (`OSError`, `subprocess.SubprocessError`, `psutil.NoSuchProcess`, `psutil.AccessDenied`)
- Timeout de 10s no fallback pgrep

**Nota:** `psutil` 5.9.8 já estava disponível no venv. `pgrep` (procps-ng 4.0.4) disponível no sistema.
- ## Cache implementado em _mt5_status() no system_health_service.py

### Problema
O health check (GET /health) chamava `_mt5_status()` que executava `mt5.initialize()` + `mt5.shutdown()` a cada requisição HTTP. Isso é ineficiente e causa instabilidade no MT5.

### Solução
Implementado cache TTL simples (30s) usando variáveis de módulo + `threading.Lock()` para thread-safety:
- `_mt5_cache`: dict com `result` e `timestamp`
- `_MT5_CACHE_TTL`: 30 segundos
- `_mt5_cache_lock`: `threading.Lock()` para acesso concorrente seguro
- `time.monotonic()` usado para medição de intervalo (imune a ajustes de relógio)

### Arquivo modificado
`web_app/services/system_health_service.py`

### Linhas afetadas
- Adicionados imports: `threading` (linha 6), `time` (linha 7)
- Adicionadas variáveis de cache: linhas 20-23
- Função `_mt5_status()` reescrita com cache: linhas 197-265

### Comportamento
1. Primeira chamada: cache miss → MT5 init → busca dados → shutdown → armazena no cache
2. Chamadas subsequentes em < 30s: retorna dado do cache (sem MT5)
3. Após 30s: próxima chamada faz cache miss → atualiza dado
4. Thread-safe: lock protege leitura/escrita concorrente
5. Resultados de erro também são cacheados (evita martelar MT5 quando está down)

### Métricas
- Antes: ~2-5s por requisição health (dependente da latência MT5)
- Depois: ~0.001s por requisição (cache hit) + ~2-5s a cada 30s (cache miss)
- Redução de ~99.9% das chamadas MT5

### Observações
- `cachetools` não está disponível no ambiente; solução caseira implementada
- Sem testes unitários existentes para este módulo; necessário criar
- 30s de stale data é aceitável para health check (dados não mudam rápido)
